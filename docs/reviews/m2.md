## Blockers
1. **Scheduled publish breaks its own cache, then publishes an empty `languages`.**
   `src/babel_lag/lake/delta.py:55` (`_write`, overwrite mode) never vacuums, so every run adds a
   full copy of `silver_live_events` and the gold tables (local: 9 Delta versions, ~1.1 GB for
   one ~200 MB table). At 48 runs/day `data/` grows ~10 GB/day, and after a slice dispatch it
   already holds `data/staging` (1.7 GB) and `silver_page_revisions` (5.7 GB).
   `.github/workflows/publish.yml:56-61,82-86` caches all of `data/` against GitHub's 10 GB repo
   cache limit, so saves fail or evict. A cold or stale restore then runs the full rollup over
   missing dump tables (`delta.py:160-163` turns them into empty tables), which writes an empty
   `gold_language_lag`. After that every run takes `LIVE_STEPS` only (`pipeline.py:69`), and a
   free run uploads `languages.json` with `row_count` 0 using `--clobber`
   (`publish.yml:69`; the envelope schema allows `minimum: 0`).
   Fix: vacuum after each overwrite in `_write` (`retention_hours=0`, as `prune_bronze` does).
   Cache only `data/state`, `data/telemetry`, `data/lineage`, `data/lake/bronze`,
   `data/lake/gold`, `data/lake/silver/silver_live_events` and `data/warehouse`, leaving out
   `data/staging`, `data/landing` and the dump-derived silver. In `site.write_all`, refuse to
   write (fail the run) when `languages` has 0 rows, so the last good release asset stays.
